# Python build and review standard

Apply this when the repository is Python. Read the repo's own conventions and the brief first. An explicit user instruction, a repo convention, or a concrete library requirement may justify a different shape; name that reason and its effect in the verdict. A passing test suite and a clean type checker do not waive these rules.

- Parse every input once where it enters: tool and CLI arguments, environment, stored rows, HTTP and LLM responses, persisted JSON. Decode it into frozen typed models (pydantic, or `@dataclass(frozen=True, slots=True)`) at that edge. Past the edge, no `dict[str, Any]` or `dict[str, object]` payloads and no `.get("key")` chains. Plain dicts belong only at serialization and persistence edges.
- Name each closed value set once, as a `Literal` alias or `StrEnum`, in the module that owns the concept. Do not type a closed set as `str` or `frozenset[str]`, and do not re-spell the literal inline.
- Do not add `Any`, `cast`, `# type: ignore` or `model_copy(update={...})` without a reason on the same line. Express state changes as typed methods or constructors the type checker can see.
- Give each value one meaning. No `Optional` that means different things in different branches, no `str | None` carrying an error message, no `bool` standing for more than two outcomes, no anonymous tuples crossing a function boundary. Return small tagged result types and branch on them with `match` and `assert_never`.
- `assert` is not a runtime guard. When code needs `assert isinstance(...)` after a read, fix the type with a typed accessor or a narrower return. Each interface follows one lookup convention: return `X | None`, or raise a named error.
- Keep the main path readable top to bottom: guard clauses with early return, then named sequential steps. A function longer than about 80 lines or nested deeper than 3 levels needs a stated reason. Use `match` for exclusive alternatives and comprehensions or set operations for simple transforms; keep loops where order, side effects or indexed errors matter.
- Extract functions that name a real operation. Avoid boolean or mode parameters that switch between separate operations, tiny pass-through wrappers, and generic templates whose callbacks outnumber the lines they save. Share an invariant through one pure function both callers use; duplicate code only when the copies must be free to differ, and say why.
- Pass shared collaborators (storage, clock, config, locks, clients) as one context object built at entry, and request inputs as one typed value. More than 6 parameters needs a reason.
- A leading underscore means private to its file. Anything another module imports is public and named without the underscore. Fix import cycles by moving code, not by hiding them behind function-level imports.
- Docstrings and comments state the contract: what the code guarantees, what it raises, and the ordering or locking it relies on. Do not narrate review rounds, plan task numbers, dates or bug history; git holds that. Text shipped to a client, such as tool descriptions and prompts, is wire, not commentary.
- Raise one exception type per meaning a caller can act on. Never branch on exception message text. Catch broadly only at a named boundary (transport, background loop, best-effort telemetry) and state why at that site.
- Ship production code only: no test doubles, no parameters or properties that exist only for tests, no stubs for future work, no configuration fields nothing reads, no dead code. Test support lives under `tests/`.
- Preserve wire and persisted shapes unless the brief changes them: public names, response fields, stored schemas and encodings, timezone-aware instants, and the difference between a missing value and an explicit null. Review readability and data meaning separately from whether tests pass.
